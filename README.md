# dss-dwh

HTTP-сервис на FastAPI для получения признаков наличия событий клиента из Oracle КХД. Сервис возвращает 15 булевых признаков за 1, 7 и 30 календарных дней относительно даты запроса, включая эту дату.

Клиент сервиса — СПР. Источники обновляются один раз в сутки. Сервис читает заранее рассчитанное материализованное представление, а не исходные таблицы.

## Схема взаимодействия

### Обработка запроса

```text
                         ┌─────┐
                         │ СПР │
                         └──┬──┘
                            │ HTTP POST
              ┌─────────────▼─────────────┐
              │ Балансировщик /           │
              │ Swarm routing mesh        │
              └──────┬───────────┬────────┘
                     │           │
           ┌─────────▼──┐   ┌────▼───────┐
           │ dss-dwh    │   │ dss-dwh    │
           │ реплика 1  │   │ реплика 2  │
           └─────────┬──┘   └────┬───────┘
                     │           │
                     │ По одному соединению
                     │           │
              ┌──────▼───────────▼────────┐
              │ Oracle                    │
              │ APP.MV_CUSTOMER_DAY       │
              └───────────────────────────┘
```

Запрос содержит ФИО, телефон, дату и номер заявки. Выбранная реплика выполняет один SQL-запрос к агрегату, преобразует числовые признаки в JSON boolean и возвращает результат. Взаимодействие синхронное. Сервис не хранит заявки и не использует кэш.

В Swarm запросы распределяет routing mesh. На двух независимых нодах нужен внешний балансировщик или существующий корпоративный шлюз с двумя upstream-адресами. Файлы проекта запускают экземпляры сервиса; отдельный балансировщик в них не разворачивается.

### Подготовка данных

```text
Ночная загрузка источников существующим ETL
                    │
          ┌─────────┴──────────┐
          ▼                    ▼
      MirLada              Гарантия
          │                    │
          └─────────┬──────────┘
                    ▼
     Обе загрузки успешно завершены
                    │
                    ▼
       Один запуск sql/05_refresh.sql
                    │
           COMPLETE, atomic=TRUE
                    │
          ┌─────────┴──────────────────┐
          ▼                            ▼
 APP.MV_CUSTOMER_DAY          APP.CUSTOMER_REFRESH_LOG
          ▲
          │ Категории

```

Ночное обновление не запускается из FastAPI. Зависимость от завершения источников настраивается в существующем ETL. До публикации нового результата API читает предыдущий агрегат.

## Данные и правила расчёта

### Источники

| Источник | Дата события | Категория |
|---|---|---|
| `DATAHUB.LADARU_MIRLADA_CUSTOMERS_FILT` | `"DATE"` | `TYPE` |
| `DATAHUB.LADA_GUARANTEE20_CUSTOMERS_FILT` | `SERVICE_DATE` | Не используется |

Оба источника содержат `FULL_NAME` и `PHONE`. SQL предполагает даты Oracle DATE либо совместимые с используемыми операциями типы. Для TIMESTAMP WITH TIME ZONE необходимо отдельно согласовать бизнес-часовой пояс до внедрения.

### Сопоставление клиента

Совпасть должны оба ключа:

```sql
LOWER(TRIM(full_name))
REGEXP_REPLACE(phone, '^8', '7')
```

- ФИО приводится к нижнему регистру; обычные пробелы по краям удаляются.
- Внутренние пробелы, `ё/е`, порядок слов не изменяются.
- В телефоне только начальная `8` заменяется на `7`.
- Символ `+`, скобки, дефисы и пробелы в телефоне сохраняются.
- `89991111111` и `79991111111` совпадут; `+7 (999) 111-11-11` и `79991111111` — нет.
- `app_number` возвращается из запроса и не участвует в поиске.
- Строки источников с пустым ключом клиента или датой исключаются из MV.

Нормализация и параметров, и источников выполняется в Oracle.

### Агрегат

Одна строка `APP.MV_CUSTOMER_DAY` соответствует сочетанию `name_key + phone_key + event_day`. Дата события округляется вниз до календарного дня через `TRUNC`. Пять колонок содержат 0 или 1: `mirlada`, `cred`, `cred_car`, `auto_care`, `guarant`.

Для точного поиска создан уникальный индекс `(name_key, phone_key, event_day)`. Повторные события клиента в один день не меняют признаки. Общий признак MirLada учитывает также категории, которых нет в справочнике.

MV рассчитывается по всей истории, присутствующей в источниках. Это не независимый архив: если источник удалил старые строки, полный пересчёт удалит соответствующие данные из MV.

### Категории

| Группа | Категории |
|---|---|
| `cred` | `кредит`; `Одобрение кредита`; `обратный звонок/Заявка на кредит`; `обратный звонок/Кредит` |
| `cred_car` | Все категории `cred` и `приобретение автомобиля` |
| `auto_care` | `Плановое ТО`; `Ремонт`; `Диагностика`; `Вопрос дилеру`; `Другое`; `обратный звонок/Автосервис`; `Шиномонтаж`; `Кузовной ремонт`; `обратный звонок/Стоимость ТО`; `Roadhelp`; `обратный звонок/Продажа запасных частей и аксессуаров` |
| `guarant` | Любое событие гарантийного источника |

Категория сравнивается с `TYPE_CATEGORY.TYPE_NAME` по правилам сравнения строк вашей БД. Сервис не выполняет для категории отдельного `LOWER` или `TRIM`.

### Временные интервалы

Для даты запроса D используются интервалы:

| Период | Условие |
|---|---|
| 1 день | `D <= event_day < D + 1` |
| 7 дней | `D - 6 <= event_day < D + 1` |
| 30 дней | `D - 29 <= event_day < D + 1` |

Для `12.02.2026`: 1 день — 12 февраля; 7 дней — 6–12 февраля; 30 дней — 14 января – 12 февраля включительно. События 13 февраля не учитываются.

Дата запроса может быть исторической. Будущие даты также не запрещены кодом: результат определяется опубликованными данными и границами интервалов. Технический диапазон входной даты: 30.01.0001–30.12.9999.

`false` означает отсутствие совпадения в опубликованном агрегате. Если день запроса ещё не загружен, сервис не отличает этот случай от отсутствия события. Контроль полноты и свежести выполняется процессом загрузки и мониторингом, а не обработчиком API.

## HTTP API

Аутентификация и API-ключ отсутствуют. Доступ к опубликованному порту предоставляется через вашу внутреннюю сеть/шлюз. Сервис слушает HTTP; TLS при необходимости завершается на внешнем шлюзе.

### POST /v1/customer-features

Заголовок: `Content-Type: application/json`.

| Поле | Тип | Правила |
|---|---|---|
| `app_number` | string | Обязательно, 1–100 символов |
| `fio` | string | Обязательно, 1–200 символов, не только пробелы |
| `phone_num` | string | Обязательно, 1–100 символов, не только пробелы |
| `date` | string | Обязательно, `DD.MM.YYYY` или `YYYY-MM-DD` |
| `cache_days` | integer/null | Необязательно, принимается и игнорируется |

Неизвестные поля запрещены. Размеры ФИО и телефона нужно сопоставить с фактическими колонками Oracle. Проверка номера телефона на количество цифр и страны в сервисе отсутствует.

Пример запроса:

```bash
curl --fail-with-body --max-time 15 \
  -X POST http://NODE_IP:8000/v1/customer-features \
  -H 'Content-Type: application/json' \
  -d '{
    "app_number": "example-001",
    "fio": "Иванов Иван Иванович",
    "phone_num": "79991111111",
    "date": "12.02.2026"
  }'
```

Пример ответа при отсутствии совпадений:

```json
{
  "app_number": "example-001",
  "has_mirlada_1day_ago": false,
  "has_mirlada_7day_ago": false,
  "has_mirlada_30day_ago": false,
  "has_mirlada_1day_ago_cred": false,
  "has_mirlada_7day_ago_cred": false,
  "has_mirlada_30day_ago_cred": false,
  "has_mirlada_1day_ago_cred_car": false,
  "has_mirlada_7day_ago_cred_car": false,
  "has_mirlada_30day_ago_cred_car": false,
  "has_mirlada_1day_ago_auto_care": false,
  "has_mirlada_7day_ago_auto_care": false,
  "has_mirlada_30day_ago_auto_care": false,
  "has_guarant_1day_ago": false,
  "has_guarant_7day_ago": false,
  "has_guarant_30day_ago": false
}
```

Для каждой группы меняется только проверяемый период. Например, `has_mirlada_7day_ago_cred` означает наличие кредитного события за семь календарных дней, включая дату запроса.

### Служебные endpoints

| Метод и путь | Назначение |
|---|---|
| `GET /health/live` | Ответ процесса `{"status":"ok"}`, без запроса Oracle |
| `GET /health/ready` | Проверяет соединение и чтение MV; `{"status":"ready"}` при успехе |
| `GET /docs` | Swagger UI |
| `GET /redoc` | Документация API |
| `GET /openapi.json` | OpenAPI-схема |

`ready` использует тот же единственный пул. Пустое MV допустимо; свежесть данных этот endpoint не проверяет. Docker healthcheck обращается к `live`, а не к Oracle.

### Коды ответа

| Код | Значение |
|---|---|
| 200 | Успешный ответ, включая отсутствие клиента |
| 422 | Некорректное тело или параметры запроса |
| 503 | Ошибка Oracle, включая недоступность, отсутствие прав или истечение ожидания соединения |
| 500 | Неожиданная структура результата либо другая внутренняя ошибка |

Ответ 503: `{"detail":"Data source unavailable"}`. Сервис не подменяет ошибку БД набором `false`. Ошибки валидации возвращают расположение и тип ошибки без отражения входных значений.

## Соединения и тайм-ауты

- Один процесс Uvicorn в контейнере (`--workers 1`).
- Пул Oracle: `min=1`, `max=1`, `increment=0`.
- Две реплики: до двух соединений пула при штатной работе.
- Получение занятого соединения ожидает до 2000 мс.
- `connection.call_timeout=3000` ограничивает один round trip к БД, а не весь HTTP-запрос.
- `tcp_connect_timeout=5`, `retry_count=0` применяются к созданию соединения.
- При старте создаётся соединение; если начальное подключение не удалось, приложение не завершит запуск.

Два запроса на одной реплике не выполняют SQL одновременно: второй ожидает соединение. Общая очередь HTTP-запросов в приложении отдельно не ограничена. Увеличение числа worker-процессов умножит число пулов. Дополнительные административные и ETL-сессии не входят в указанный лимит.

Целевая нагрузка — до 5 RPS. Фактическая пропускная способность зависит от времени SQL и сети; её нужно измерять на вашей Oracle. Распределение запросов между репликами не гарантирует равную загрузку.

## Подготовка Oracle

### Проверка источников

```sql
SELECT table_name, column_name, data_type, data_length
FROM all_tab_columns
WHERE owner = 'DATAHUB'
  AND table_name IN (
    'LADARU_MIRLADA_CUSTOMERS_FILT',
    'LADA_GUARANTEE20_CUSTOMERS_FILT'
  )
ORDER BY table_name, column_id;
```

Проверяются `FULL_NAME`, `PHONE`, `TYPE`, `"DATE"`, `SERVICE_DATE`, глубина истории и способ публикации загрузок.

### Пользователи и выполнение SQL

DBA заранее создаёт APP с квотой и правами создания объектов и API_USER с правом подключения. Пароли и tablespace определяются DBA; скрипты проекта пользователей не создают.

1. Владелец источников или DBA выполняет `sql/00_source_grants.sql`.
2. Под APP последовательно выполняются файлы 01–04.
3. Файл 02 сразу читает источники и заполняет MV; запускать после завершения обоих источников.
4. Файл 03 выдаёт API_USER право чтения MV. Доступ API_USER к исходным таблицам не требуется.

Пример с SQL*Plus, пароль вводится интерактивно:

```bash
sqlplus -L APP@//oracle-host:1521/service_name
```

В открытой сессии:

```sql
@sql/01_categories.sql
@sql/02_materialized_view.sql
@sql/03_index_and_grants.sql
@sql/04_refresh_log.sql
```

Скрипты создания выполняются один раз и не являются идемпотентными. Повторный запуск CREATE для существующего объекта завершится ошибкой. Для другой схемы замените APP во всех SQL и в `main.py`; схема агрегата не задаётся переменной окружения.

Для SQL с кириллицей согласуйте кодировку SQL*Plus и файлов UTF-8. DBA проверяет допустимую длину индексного ключа для реальных размеров колонок.

### Проверка результата

```sql
SELECT COUNT(*) FROM app.mv_customer_day;

SELECT event_day, mirlada, cred, cred_car, auto_care, guarant
FROM app.mv_customer_day
WHERE name_key = LOWER(TRIM(:fio))
  AND phone_key = REGEXP_REPLACE(:phone, '^8', '7')
  AND event_day >= DATE '2026-01-14'
  AND event_day < DATE '2026-02-13'
ORDER BY event_day;
```

Bind-параметры `:fio` и `:phone` задаются в используемом SQL-клиенте. Результат сравнивается с исходными таблицами.

Для приватного репозитория используйте настроенную Git-авторизацию или SSH. Токены не добавляются в URL репозитория.

```bash
python3.12 -m venv .venv
. .venv/bin/activate
```

Тесты не подключаются к Oracle. В `requirements.txt` заданы диапазоны версий, поэтому повторная сборка из того же коммита может установить другие совместимые версии. Повторяемость развёртывания обеспечивает использование уже собранного образа по digest.

### 3. Войти в GHCR для публикации

Для ручной публикации нужен GitHub PAT classic с `write:packages`; для скачивания приватного образа — `read:packages` и доступ к пакету. Права Git-репозитория и контейнерного пакета проверяются отдельно. См. [GitHub Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

```bash
read -rsp 'GHCR publish token: ' GHCR_TOKEN
printf '\n'
printf '%s' "$GHCR_TOKEN" | docker login ghcr.io -u DonFilini --password-stdin
unset GHCR_TOKEN
```

### 4. Собрать и отправить образ

Команды ниже создают образ для Linux amd64. Все узлы в этом примере должны поддерживать эту архитектуру.

```bash
export IMAGE_TAG="$(git rev-parse --short=12 HEAD)"
export IMAGE="ghcr.io/donfilini/dss-dwh:${IMAGE_TAG}"

docker buildx build \
  --platform linux/amd64 \
  --label org.opencontainers.image.source=https://github.com/DonFilini/dss-dwh \
  --label org.opencontainers.image.revision="$(git rev-parse HEAD)" \
  --tag "$IMAGE" \
  --push .
```

Для ARM-хостов выбирайте соответствующую платформу и проверяйте доступность зависимостей. Никакие credentials Oracle при сборке не нужны; они передаются только при запуске контейнера.

### 5. Зафиксировать опубликованный образ

```bash
docker pull "$IMAGE"
docker image inspect "$IMAGE" --format '{{index .RepoDigests 0}}'
```

Команда выводит адрес вида:

```text
ghcr.io/donfilini/dss-dwh@sha256:ACTUAL_DIGEST
```

Скопируйте фактический адрес в `DSS_DWH_IMAGE`. Тег служит удобным именем, digest однозначно определяет содержимое. Не используйте буквальный placeholder `ACTUAL_DIGEST`.

## Развёртывание в Docker Swarm

Этот вариант использует **только `stack.yml`**. Не запускайте параллельно независимый Compose-вариант на тех же хостах: это создаст дополнительные экземпляры и конфликт порта 8000.

### 1. Подготовить Swarm

Если кластер уже существует, этот шаг пропускается. На будущем manager:

```bash
docker swarm init --advertise-addr MANAGER_IP
docker swarm join-token worker
```

На worker выполните команду `docker swarm join`, которую вывел manager. Затем на manager:

```bash
docker node ls
```

Для двух реплик на разных машинах нужно минимум два доступных узла. `spread: node.id` — предпочтение распределения, а не жёсткая гарантия размещения на разных узлах. Текущий файл не ограничивает одну задачу на узел. Один manager также не обеспечивает отказоустойчивость управляющего контура; топология manager-узлов относится к настройке кластера.

### 2. Получить конфигурацию

На manager получите репозиторий или доставьте `stack.yml`, `compose.nodes.yml` и `.env.example` вашим способом. Для запуска готового образа Python и SQL*Plus на manager не требуются.

На manager задайте параметры в окружении shell. Укажите фактический образ с digest:

```bash
export DSS_DWH_IMAGE=ghcr.io/donfilini/dss-dwh@sha256:ACTUAL_DIGEST
export ORACLE_USER=API_USER
export ORACLE_DSN=oracle-host:1521/service_name
read -rsp 'Oracle password: ' ORACLE_PASSWORD
printf '\n'
export ORACLE_PASSWORD
```

Переменные должны быть заданы в той же shell-сессии, из которой выполняется deployment.

### 3. Авторизовать скачивание приватного образа

На manager под тем же пользователем Docker, который выполняет deployment:

```bash
read -rsp 'GHCR read token: ' GHCR_TOKEN
printf '\n'
printf '%s' "$GHCR_TOKEN" | docker login ghcr.io -u DonFilini --password-stdin
unset GHCR_TOKEN
```

### 4. Применить конфигурацию

Docker Compose читает `.env`; `docker stack deploy` не выполняет автоматическую загрузку этого файла. Для Swarm используются переменные, экспортированные на шаге 2. Значения переменных не нужно вставлять в YAML вручную.

```bash
docker stack deploy --with-registry-auth -c stack.yml dss-dwh
```

`--with-registry-auth` передаёт registry-авторизацию узлам для скачивания образа. Команда выполняется на manager. Если используется `sudo`, учитывайте, что оно может сбросить экспортированное окружение; выполняйте Docker-команды пользователем с уже настроенными правами.

### 5. Проверить запуск

```bash
docker stack services dss-dwh
docker service ps dss-dwh_api --no-trunc
docker service logs --tail 100 dss-dwh_api
curl --fail --max-time 5 http://MANAGER_IP:8000/health/live
curl --fail --max-time 15 http://MANAGER_IP:8000/health/ready
```

Ожидается две работающие задачи (`2/2`). Swarm routing mesh принимает запросы на опубликованный порт узлов и направляет их в задачи сервиса. Для внешней отказоустойчивости единая точка входа должна учитывать доступность самих узлов.

## Развёртывание на двух независимых нодах

Этот вариант использует **только `compose.nodes.yml`**. Swarm не требуется. На каждой ноде запускается один контейнер с одним соединением Oracle; две ноды дают два экземпляра.

### 1. Доставить конфигурацию на каждую ноду

На NODE_1 и NODE_2 нужны Docker Engine, Compose v2, `compose.nodes.yml` и локальный `.env`. Можно клонировать репозиторий либо доставить эти файлы отдельно.

На обеих нодах укажите одинаковый `DSS_DWH_IMAGE` с digest. Credentials могут различаться, если Oracle-пользователям предоставлены одинаковые права чтения MV.

### 2. Войти в GHCR на каждой ноде

Повторите команду `docker login` с токеном `read:packages` на каждой машине. Передача registry-авторизации между независимыми Docker-хостами автоматически не происходит.

### 3. Запустить по одному экземпляру

На **каждой** ноде из каталога конфигурации:

```bash
docker compose --env-file .env -f compose.nodes.yml -p dss-dwh pull
docker compose --env-file .env -f compose.nodes.yml -p dss-dwh up -d
docker compose --env-file .env -f compose.nodes.yml -p dss-dwh ps
docker compose --env-file .env -f compose.nodes.yml -p dss-dwh logs --tail 100 api
curl --fail --max-time 5 http://127.0.0.1:8000/health/live
curl --fail --max-time 15 http://127.0.0.1:8000/health/ready
```

Затем с машины, имеющей сетевой доступ:

```bash
curl --fail --max-time 15 http://NODE_1_IP:8000/health/ready
curl --fail --max-time 15 http://NODE_2_IP:8000/health/ready
```

Внешнему балансировщику задаются два upstream: `NODE_1_IP:8000` и `NODE_2_IP:8000`. `/health/live` проверяет процесс, `/health/ready` — также Oracle. Частые проверки ready конкурируют с рабочими запросами за единственное соединение; период проверок выбирается с учётом этого.

Compose самостоятельно не переносит контейнер с отказавшей ноды на другую. `restart: unless-stopped` перезапускает завершившийся процесс на том же хосте; статус unhealthy сам по себе не является причиной перезапуска в обычном Docker Compose.

## Обновление и откат

### Docker Swarm

1. Соберите и опубликуйте новый образ.
2. Сохраните адрес предыдущего образа для отката.
3. Экспортируйте новый `DSS_DWH_IMAGE` в deployment-сессии manager.
4. Задайте также Oracle-переменные и повторите `docker stack deploy` из инструкции выше.
5. Проверьте `docker service ps`, логи и ready.

Задачи обновляются по одной с `stop-first`: старая останавливается перед запуском новой. В этот момент остаётся одна реплика. Эта настройка не обещает отсутствие ошибок для уже выполнявшихся запросов, но не создаёт дополнительную реплику для обычного обновления. Автоматический rollback реагирует на сбой задачи/healthcheck, а не на все возможные бизнес-ошибки.

Ручной откат последнего обновления:

```bash
docker service rollback dss-dwh_api
docker service ps dss-dwh_api
```

После отката верните предыдущий образ также в deployment-переменные вашей инфраструктуры, иначе следующий deployment снова применит новый образ.

### Независимые ноды

1. Исключите NODE_1 из балансировки и дождитесь завершения её активных запросов средствами вашего балансировщика.
2. На NODE_1 измените образ в `.env`, выполните `pull` и `up -d`.
3. Проверьте ready и тестовый запрос, верните ноду в балансировку.
4. Повторите для NODE_2.

Для отката задайте предыдущий digest в `.env` и повторите `pull`/`up -d` по той же процедуре. Одновременное обновление обеих независимых нод создаёт период полной недоступности.

Пароль Oracle тоже передаётся при создании контейнера. После изменения переменных примените конфигурацию заново; для Compose при необходимости используйте `up -d --force-recreate`. Смена пароля в самой Oracle выполняется отдельно DBA.

## Ночное обновление данных

Окно обработки — 23:00–01:00 по согласованному бизнес-времени. Время включает загрузку источников и пересчёт MV. В проекте нет встроенного расписания или определения ETL-задач.

После подтверждения обеих загрузок ETL запускает под APP:

```bash
sqlplus -L APP@//oracle-host:1521/service_name @sql/05_refresh.sql
```

Для автоматизации применяйте штатное хранение credentials ETL или Oracle Wallet. Пример выше интерактивный и не передаёт пароль в аргументах процесса.

- Одновременно запускается только один refresh; сам скрипт не содержит блокировки от параллельных запусков.
- Источники должны представлять согласованный завершённый набор данных при чтении.
- Refresh использует `COMPLETE` и `atomic_refresh => TRUE`.
- Журнал содержит RUNNING, SUCCESS или FAILED с кодом ошибки.
- При аварийном завершении процесса запись может остаться RUNNING.
- Запись SUCCESS отражает успешное выполнение refresh, а не доказательство полноты источников.
- Начальное заполнение через CREATE MV не записывается в этот журнал.
- Ошибка следующей загрузки не заставляет API перестать читать предыдущий агрегат.

Проверка:

```sql
SELECT started_at, finished_at, status, error_code
FROM app.customer_refresh_log
ORDER BY started_at DESC
FETCH FIRST 20 ROWS ONLY;

SELECT MAX(finished_at) AS last_success
FROM app.customer_refresh_log
WHERE status = 'SUCCESS';
```

Полный пересчёт читает всю доступную историю источников. На ваших объёмах необходимо измерить время, расход undo/temp и влияние на КХД. API эти операции не выполняет. При необходимости DBA организует сбор статистики MV и индекса после обновлений.

## Проверка и диагностика

### Приёмочная проверка

- Проверить клиента с событиями каждого типа и клиента без совпадений.
- Проверить границы 1/7/30 дней и исключение следующего дня.
- Проверить историческую дату с более поздними событиями клиента.
- Проверить старый опубликованный агрегат во время ночной загрузки и неудачного refresh.
- Проверить 503 при ошибке Oracle.
- Провести нагрузочный тест до 5 RPS на разных клиентах и датах.
- Проверить фактический план SQL и использование индекса вместе с DBA.
- Проверить чтение Oracle с обеих реплик и журнал ночных загрузок.

### Типовые проблемы

| Признак | Что проверить |
|---|---|
| Контейнер не запускается, KeyError ORACLE_* | Все три Oracle-переменные заданы и попали в deployment |
| Не удаётся скачать image | Адрес/digest, права GHCR, login, доступ узлов к registry |
| Swarm task Rejected / No such image | `--with-registry-auth`, доступный образ нужной архитектуры |
| ORA-00942 / 503 | MV создано именно в APP, API_USER имеет SELECT |
| 503 при параллельных запросах | Время SQL, ожидание единственного соединения, нагрузка readiness |
| Live 200, ready 503 | Процесс работает, но запрос Oracle не проходит |
| Все признаки false | Точное ФИО/телефон, даты, наличие истории, свежесть агрегата |
| Неполные текущие сутки | Источники обновляются раз в день; текущие события могли ещё не попасть в MV |
| Две задачи на одной Swarm-ноде | Spread является предпочтением; проверить доступные узлы и placement |
| Refresh не уложился в окно | Время ETL и refresh, объём истории, ресурсы БД |
| RUNNING остался в журнале | Проверить, жив ли процесс refresh; не запускать повторно вслепую |

Сервис пишет код ошибки Oracle без bind-параметров. Uvicorn access-log отключён. Встроенного экспортера метрик и проверки максимального возраста MV нет; контроль ошибок, задержек и последнего успешного refresh организуется внешним мониторингом.

## Локальный запуск и тесты

После создания виртуального окружения и установки зависимостей задайте переменные в Bash:

```bash
export ORACLE_USER=API_USER
export ORACLE_DSN=oracle-host:1521/service_name
read -rsp 'Oracle password: ' ORACLE_PASSWORD
printf '\n'
export ORACLE_PASSWORD

python -m uvicorn main:app --host 127.0.0.1 --port 8000 --workers 1
```

Для локального запуска нужен доступ к Oracle и готовому MV. Файл `.env` не читается `main.py` автоматически; его обработку в deployment выполняет Compose.

Для unit-тестов credentials не нужны:

```bash
python -m pytest -q
```

Тесты подменяют Oracle и проверяют интервалы, передачу ключей клиента, выдачу 15 признаков, отсутствие аутентификации, ошибки запроса и БД, игнорирование cache_days. Они не подтверждают совместимость DDL с вашей схемой, фактическую производительность или сетевую доступность Oracle из production-контейнеров.
